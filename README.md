# Vyoma SSA - Orbital Risk Intelligence Platform

Vyoma SSA is a React, Three.js, and FastAPI Space Situational Awareness research platform for visualizing orbital data, screening trajectories for close approaches, and reporting the results. This working copy preserves the existing application and adds Stage 2A trajectory screening, Stage 2B collision-probability capability, and Stage 3 independent ML estimates without creating a second frontend or backend.

The application combines an interactive 3D Earth environment, TLE-backed SGP4 propagation, separate deterministic heuristic proxies, trajectory-derived TCA and miss distance, a Foster 2D Pc research method, an ESA event log-risk estimator, and PDF/CSV/JSON report downloads. Live Pc is unavailable because the current TLE source supplies no covariance and measured object dimensions/HBR are absent. ESA log-risk is not Pc and is not calibrated for operational risk alerts.

## Current Status

Stage 3 status (2026-10-17): Stage 2A trajectory screening and Stage 2B Foster 2D Pc are preserved. The v2 ESA event log-risk estimator is Ridge, selected by validation MAE from Ridge/HGB candidates and trained with disjoint mission-grouped splits. On the 3,832-event held-out mission test set, Ridge MAE is 6.8935 log10 units and Spearman correlation is 0.4424; at the fixed log-risk threshold it predicts 0 of 145 high-risk labels. This is a weak historical-proxy ranking/regression signal, not a collision-probability model or alert; do not use it for operational decisions. Collision Analysis displays the inference inputs and units when a prediction is available. Normal TLE events still return structured Pc-unavailable reasons. Software checks do not establish operational accuracy or readiness.

The baseline audit in `docs/HYBRID_BASELINE_AUDIT.md` records the pre-Stage 1 source state. Use `docs/PHYSICS_DATA_MODEL.md` for the current data and provenance contract, `docs/STAGE3_ML_MODEL_CARD.md` for training, held-out metrics, intended use, and limitations, and `docs/HYBRID_SYSTEM_STATUS.md` for current module integration, cache identity, and verification commands. Other bundled implementation reports are historical records of the earlier prototype.

## Features

- Persistent mission-console shell with Home, Visualization, Smart Filter, Collision Analysis, Maneuver, Historical Analytics, and Reports pages.
- Preserved 3D globe with procedural Earth texture, cloud layer, atmosphere, glow, fog, stars, orbit shells, radar sweep, camera controls, bloom, and vignette.
- Efficient instanced active-object markers rendered as small glowing satellite bodies with solar-panel silhouettes.
- Efficient instanced debris markers rendered as colored glowing fragments using dark red, amber, purple, cyan, and gray tones.
- Catalog-backed autocomplete global search for object names, NORAD-like IDs, bands, categories, orbit types, altitude, inclination, and velocity.
- Visualization filters for active objects, debris, LEO, MEO, GEO, and risk severity.
- 3D visualization heatmap using explicitly heuristic orbital-shell scores generated by the backend.
- Smart Filter workflow with deterministic catalog heuristics, screening-proxy review-list summaries, model availability, and independent ML estimates for physical trajectory events; it reports no model confidence.
- Collision Analysis displays SGP4 trajectory-derived TCA, miss distance, and relative state when a pair meets the configured threshold within the screening horizon. It displays Foster 2D Pc only when valid covariance and HBR inputs are supplied; current TLE events explicitly report those inputs unavailable. Heuristic proxies remain separate.
- Each valid physical event carries an explicitly internal, geometry-only ORION review-priority category (LOW/MEDIUM/HIGH/CRITICAL); invalid/boundary inputs return REVIEW_REQUIRED and missing evidence returns UNCLASSIFIED. These are not Pc or operational collision-risk levels. Search, sort, pair/status/Pc/priority filters, event details, and exports preserve the decision rationale. See `docs/REVIEW_PRIORITY_POLICY.md`.
- Collision Analysis also provides a standalone NASA CARA CDM reference-assessment workflow. It evaluates the selected CDM's own identities, TCA states, covariance, and HBR; it does not bind the historical/reference result to a live TLE screening event. Source-reported Pc remains separate from ORION's Foster 2D result.
- The default trajectory screen covers 24 hours from request UTC with 60-second sampling and a 25 km event threshold; all are exposed in API metadata, with request overrides available.
- No live covariance or measured HBR is available from the current source, so live Pc remains unavailable. Explicitly sourced covariance/HBR inputs are required for the research Foster 2D method. ML predictions are unavailable when optional dependencies, a compatible artifact, or required Stage 2A features are missing.
- Maneuver page reports that Stage 2A encounter geometry does not include covariance or validated maneuver dynamics.
- Historical analytics shows heuristic score distributions and proxy summaries, not physical conjunction probabilities.
- Report downloads for mission PDF/JSON, trajectory-assessment CSV, heuristic-proxy CSV, and selected-event PDF.
- Offline synthetic fallback data for visualization continuity if the backend is unavailable; records are marked `[DEMO]` and have no propagated state vectors. The offline path does not create local conjunction or maneuver records.

## Frontend

The frontend is a Vite React application. `src/App.jsx` owns the mission-console shell, page navigation, global search, watchlist persistence, settings persistence, API loading, report downloads, and page-level state. Scene rendering is isolated under `src/components/Scene`, while HUD and analytics panels live under `src/components/UI`.

The existing globe implementation is preserved in `SSAScene.jsx`, `Earth.jsx`, `OrbitShells.jsx`, `RiskHeatmap.jsx`, `RadarSweep.jsx`, and `SatelliteField.jsx`. Stage 1 updates source/score semantics in the existing components without replacing the visualization stack.

The frontend API client in `src/api/ssaClient.js` calls FastAPI at `http://127.0.0.1:8001` by default. A `VITE_API_BASE` environment variable or Vite `.env` override continues to take precedence.

## Backend

The backend is a FastAPI application under `backend/app`.

Main services:

- `tle_provider.py`: Fetches and caches CelesTrak GP/TLE records, with separately identified bundled fallback TLE records.
- `orbit.py`: Propagates valid TLE records using SGP4 and records TEME states, epochs, units, validity, and propagator metadata. It also computes separately tagged heuristic scores and visualization parameters.
- `risk.py`: Builds derived heuristic orbital-shell risk cells and score-extrapolation forecast frames; these are not future orbital propagation.
- `conjunction.py`: Retains stable-ID catalog heuristic proxies for Smart Filter and historical views. It does not label proxy ranks as physical conjunction risk.
- `trajectory_screening.py`: Propagates WGS-72 SGP4 states in TEME over the configured horizon, generates spatial-hash candidates, refines closest approach, and returns provenance-tagged TCA/miss-distance results with a separate Pc status object.
- `collision_probability.py`: Validates covariance/HBR inputs and computes the Foster 2D circular-region integral; missing live covariance/HBR returns structured unavailable status.
- `review_priority.py`: Applies a configurable and versioned internal geometry-only event review queue policy; it does not consume Pc or ESA ML output.
- `ai/training.py`: Reproducibly reads the ESA CSV from its ZIP, creates event-level train/validation/test partitions, fits Ridge and HGB estimators, measures held-out metrics, and writes a hash-verified artifact plus metadata.
- `ai/features.py`, `ai/inference.py`: Adapt the unchanged Stage 2A TEME encounter result to the model feature schema and produce a separate, provenance-tagged ML estimate; no orbital mechanics is performed by the ML service.
- `reports.py`: Generates separate proxy and trajectory-assessment reports with Pc status and provenance fields.

### Standalone CDM reference demonstration

Use the project-local NASA CARA reference fixture at `backend/tests/fixtures/nasa_cara_pc_reference.cdm`. It is the public CARA Pc test case `000020580_conj_000002017_20230613_001923_20230608_063715.cdm`, retained for repeatable parser and Foster-reference checks; it is not a live conjunction record. Source attribution and the reference-only use are documented beside the fixture in `backend/tests/fixtures/README.md`.

In Collision Analysis, upload that file, enter `NASA CARA public Pc test CDM` as the source label, explicitly select the independent-covariance assumption, and submit **Evaluate standalone CDM Pc**. The supplied case yields an ORION result near `1.862233533366684e-05` and reports the CDM's `1.862e-05` separately. The calculation remains subject to the displayed assumptions and warnings and is not NASA operational software.

For a backend running on a non-default port, set `VITE_API_BASE` before starting Vite (for example, `$env:VITE_API_BASE = 'http://127.0.0.1:8002'`). The environment override takes precedence over the default `http://127.0.0.1:8001`.

## Run Locally

From the repository root, run `.\scripts\start-dev.ps1` in PowerShell. It starts the backend with `backend\.venv` and Vite in two visible windows on ports 8001 and 5173, fails if either port is occupied, and verifies `/api/version` against the current commit before reporting ready. The footer compares frontend/backend commit IDs and warns when they differ or the backend cannot be reached. Run `.\scripts\stop-dev.ps1` to stop only the process trees recorded by that launcher.

Open two PowerShell terminals.

## Notes and Limitations

- Live CelesTrak access depends on network availability. The backend uses separately identified bundled fallback TLE records; the frontend's offline catalog/forecast fallback is synthetic demo data.
- SGP4 TLE trajectories can be stale or inaccurate. The configured horizon, sampling interval, 30 km/s relative-speed bound, screening threshold, input catalog, and candidate limits define the scope of each result. A partial run is not a complete search.
- Trajectory and Pc outputs are not operational conjunction assessments. Current TLE inputs have no covariance or HBR, so normal live Pc is unavailable. See `docs/CONJUNCTION_SCREENING_METHOD.md`, `docs/COLLISION_PROBABILITY_METHODS.md`, and `docs/PHYSICS_DATA_MODEL.md`.
- The PDF report engine is lightweight and self-contained so the backend does not require ReportLab or other optional PDF dependencies.
- The project currently uses in-memory/cache-backed data services rather than a persistent SQLite database file.
